# 참고 하네스 검토: Yuul-Jung/fpga-soc-harness-gpt

검토일: 2026-11-02 (KST) · 대상 커밋: `e57d0966941fdbf4db8e4b28c701bc780c004a69` · 방식: 읽기 전용 복제본, 저장소에 쓰지 않음

등급은 HARNESS §2를 따른다. **L3** = 파일 본문을 직접 열어 읽음, **재현** = 이 세션에서 직접 돌려 확인, **미검증** = 확인하지 못함.
"내 판단:"은 사실이 아니라 근거를 붙인 판단이다.

## 1. 한 줄 요약

GPT 하네스는 **LLM 없이 도는 결정적 Python 파이프라인**(GitHub Actions cron)이다. 강점은 *산출물 계약*(JSON 출력 4종, 해시, 라이선스 게이트, 전압 경고)과 *과거 산출물 전수 재검사*다. 약점은 *읽지 않고 분류한다*는 점(메타데이터·키워드만 본다)이고, 실제 캡스톤은 1건(smart_fan)이다. 우리 하네스는 반대로 *LLM이 원문을 읽는다*는 강점이 있고 *산출물 계약과 전수 재검사가 약했다*. 그래서 서로의 약한 쪽을 채운다.

## 3. 적대적 검토: 실제로 확인된 문제

### 3-1. CI가 "커밋에 없는 산출물"을 단언한다 — **재현**
`verify.yml`은 `site/capstones/instrument_pulse_counter/verification.json`을 단언하지만 그 캡스톤은 저장소에 없다. 복제본을 임시 폴더에 복사해 `review --offline`, `factory`를 돌리면 `instrument_pulse_counter`가 **그때 생성된다** (재현). 즉 통과 여부가 `catalog/discovered.json`(공개 검색 결과)의 내용에 달려 있다.
- 내 판단: 검증 대상이 *커밋된 입력이 아니라 CI 안에서 만들어진 파생물*이다. 같은 커밋을 다시 돌려도 검색 목록이 바뀌면 결과가 달라질 수 있어 재현성이 약하다.
- 우리 쪽 대응: 캡스톤은 반드시 커밋된 `capstone.json`이 원본이고, CI는 생성물을 단언하지 않고 **원본을 검증**한다.

### 3-2. 분류가 키워드 가중치라 점수가 의미를 과장한다 — **재현**
`review.py`의 `classify()`는 저장소 이름 6점·설명 2점·파일명 1점 키워드 합이다. 재현 결과 11건 중 `Shubhayu-Das/VL504-project`가 `quality_score` 100이다. 점수 식은 HDL 수, xdc 유무, 테스트벤치 파일 이름 유무, README 이름 유무, 라이선스다. **어떤 파일도 읽지 않고** 얻은 값이다.
- 내 판단: 100점이라는 숫자는 "열어 보면 좋을 가능성"일 뿐 품질이 아니다. HARNESS §9가 이미 금지하는 "숫자로 품질을 단정"에 해당한다. 방식은 *후보 발굴*에는 쓸 만하고 *평가*에는 쓰면 안 된다.
- `instrument_pulse_counter`의 `provenance`는 근거 저장소를 "영감"이라 적는다. 실제로는 점수 조건을 통과한 저장소 하나가 생성 트리거일 뿐 설계 근거가 아니다. 근거를 장식으로 달면 §6의 출처 원칙이 약해진다.

### 3-3. 계통도가 문제를 숨긴다 — L3 (코드 읽음)
`svg_diagram()`은 2열 격자에 모듈을 순서대로 놓고, 연결은 *상자 중심선 사이 직선*이다. 방향·버스·신호 묶음 구분이 없고 선이 상자를 가로지를 수 있다. 연결 12개짜리 smart_fan의 상자 좌표로 선분과 상자의 교차를 계산하면 `clock_reset→peripheral`의 두 선(clk, rst)이 `interconnect`와 `gpio_ctrl` 상자를 지나 총 4건이 교차한다 (재현, 직접 계산).
- 내 판단: 우리 계통도(열 배치, 링크 라벨)가 더 읽기 쉽다. 이 점은 가져오지 않는다.

### 3-4. 자동 커밋과 되돌릴 수 없는 이력
Actions가 main에 직접 커밋한다 (`contents: write`). 생성물과 원본이 같은 브랜치에 섞이고, 검색 결과 갱신 커밋이 매시간 쌓인다.
- 내 판단: 우리는 `docs/`를 git에 올리지 않고 CI가 만들게 해 이 문제를 피했다. 감사 워크플로는 **읽기 전용**으로 만든다.

### 3-5. 날짜 처리와 로그 — L3
`research.py`는 `utc_hour()`로 회전 인덱스를 만든다. 결정적이라 재현은 쉽지만, 같은 시각에 두 번 돌면 같은 질의를 던진다. 이력은 최근 240건으로 잘린다.
- 영향은 작다. 가져올 필요는 없다.

### 3-6. 검증 범위의 한계 (스스로 인정한 것 포함)
- 커밋된 `verification.json`: `rtl_simulation: pass`, `software_test: pass`, 나머지 `not_run` (L3, 기록 시각 2026-11-02T04:24Z). 합성·구현·타이밍·보드는 없다. 이 기록은 **내가 재실행한 것이 아니다** (iverilog 없음).
- `validate.py`는 테스트 스펙에서 `rtl_success` 문자열이 stdout에 *들어 있는지*만 본다. testbench가 `FAIL`을 출력해도 다른 곳에 성공 문자열이 있으면 통과할 수 있다. 우리는 `PASS`로 시작하고 `FAIL`이 없을 것을 모두 요구한다.

### 3-7. 미검증
- 최신 Actions 실행 결과와 Pages 배포 여부: 이 세션에서 해당 저장소의 API 접근이 허용되지 않아 **확인하지 못했다**.
- `library/`의 `pulse_event_meter` 시뮬레이션 통과 여부: 재현하지 못했다 (iverilog 없음). 코드는 읽었고 구조는 정상으로 보인다 (2-FF 동기화, 경계 클럭 처리 있음).

## 5. 핸드오프 원칙 중 우리가 가장 크게 어긋나 있던 것

핸드오프의 기본 대상은 **MicroBlaze V + AXI4-Lite**이고 프로젝트가 *동결 주소맵*을 정했다. 그런데 우리 두 캡스톤은 자체 버스 `mmio-lite`를 `0x1000_xxxx`에 두었다.
- 파일럿으로는 정당했다 (CPU 없이 시뮬레이션하려고). 하지만 *이 사실을 문서와 기계가 모두 알지 못했다.*
- v0.6 결정: (1) 동결 주소맵을 `config/soc_address_map.json`에 두고, (2) 명세에 `integration`을 필수로 만들며, (3) 동결 맵과 다른 캡스톤에는 문서에 **적합하지 않음**을 표시한다.
- **정정 (2026-11-02)**: 이 절의 v0.6 초판은 틀린 데가 있었다. ① 동결 맵을 L11까지 8개 영역으로 적었으나 프로젝트는 이미 `[00]~[15]`(인터럽트 In0~In12, 시험 슬롯 `[3F]`)까지 배정했다 → `mbv-frozen-v2`로 고쳤다. ② 새 주변장치용 빈 슬롯으로 `0x4007_0000`을 제안했으나 그 주소는 PWM(`[07]`)이 쓴다 → 빈 슬롯은 `[16]`(`0x4016_0000`)부터다. ③ 초판은 gpio·uart 레지스터 오프셋을 그대로 쓸 수 있다고 적었으나, 우리 `mmio-lite` 레지스터 배치는 AMD AXI GPIO·UART Lite와 다르므로 그대로 꽂히지 않는다 → 이식은 드라이버 수정 또는 IP 표준 래핑이 필요하다.
- 교훈: 프로젝트 쪽이 앞서 나가는 자료(주소맵, IP 표준)는 하네스가 추측하지 말고 프로젝트 문서에서 읽어 `config/`에 옮기며, 우선권은 프로젝트 문서에 있다(HARNESS §17).
- 변환 다리(`mmio-lite` → AXI4-Lite)는 `library/rtl/axil_regs.v`가 슬레이브 쪽 절반이다. 단, 이것은 사용자의 IP 표준(`config/ip_standard.json`: 관리 영역 `0xFFF0~0xFFFC`, ID/VER/IRQ)을 따르지 않는다. 마스터 쪽 다리와 IP 표준 적합 래퍼는 gap이다.

## 6. 이 문서가 하지 않은 것

- GPT 저장소를 수정하거나 푸시하지 않았다.
- 그 저장소의 코드를 우리 저장소에 복사하지 않았다. 형식(필드 이름과 계약)만 참고했다.
- 하드웨어 동작을 주장하지 않는다.
